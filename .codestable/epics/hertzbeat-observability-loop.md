# HertzBeat 监控闭环

## 起点

联乾已经能够将资产创建或更新为 HertzBeat 监控任务，并保存 HertzBeat `monitorId`；但资产运行状态仍可能被联乾本地巡检写入，告警仍是平台独立数据，指标只存在于 HertzBeat，普通用户还需要进入底层组件查看真实监控结果。

## 目标

联乾成为唯一日常运维入口：用户只在联乾维护项目、环境和服务；HertzBeat 在后台负责采集、状态判定、指标和告警；联乾以可恢复、幂等且可观察的同步任务持续投影这些运行数据。管理员仍可进入 HertzBeat 做高级配置和排障。

## 范围

- 将联乾项目、环境、资产 ID 作为受管标签同步到 HertzBeat；一个联乾资产首期只对应一个 HertzBeat `monitorId`。
- 统一手动和定时同步的运行契约，记录每次尝试、成功、失败和部分成功结果，并避免并发任务重复写入或旧结果覆盖新结果。
- 定时从 HertzBeat 回写监控可用状态、最近采集时间和同步时效信息。
- 将 HertzBeat 明确返回的活动告警和已恢复告警同步为联乾告警事件，保证重复同步幂等且不覆盖人工处置状态。
- 提供资产详情监控视图，展示可用性、最近采集时间、同步状态、核心指标最新值和最近一小时趋势。
- 不具备集成管理能力的会话不展示底层组件入口；当前单一管理员会话保留 HertzBeat 与 VictoriaMetrics 入口。底层组件访问仍依赖组件自身认证。
- 本地巡检继续生成巡检记录，但不得覆盖 HertzBeat 管理资产的主运行状态。
- HertzBeat 不可用或响应不完整时保留最近一次有效数据，并明确标记数据陈旧或未知，不阻断平台业务管理。

## 非目标

- 本 Epic 不实现完整 CMDB、自动发现、跨多个 HertzBeat 集群或一个资产绑定多个监控任务。
- 不在联乾中复制 HertzBeat 全部高级监控配置表单。
- 不以 VictoriaMetrics 作为首期直接查询入口；首期使用当前 HertzBeat 2.0 API，后续可替换指标适配器。
- 不实现短信、邮件等通知渠道配置，通知仍由 HertzBeat 管理。
- 不实现完整多角色 RBAC、平台代理登录或绕过 HertzBeat 自身认证；本期只控制联乾导航可见性。
- 不通过“告警从活动列表消失”推断恢复，也不在外部查询失败、分页不完整或部分解析失败时批量关闭告警。

## 验收标准

- 在联乾新增并同步资产后，用户无需进入 HertzBeat 即可看到真实监控状态、同步时效和核心指标。
- HertzBeat 监控异常后，联乾资产状态和告警列表在 60 秒同步周期内更新；HertzBeat 明确返回 `resolved` 后，原告警外部生命周期更新为已恢复，不新增重复记录。
- 连续执行状态、告警和指标同步不会产生重复资产映射或重复告警；手动与定时任务并发时只有一个运行获得写权限，旧运行结果不能覆盖较新的成功结果。
- 联乾本地巡检执行后不再覆盖已同步资产的 HertzBeat 主状态；未同步资产仍可由本地巡检维护状态。
- 资产详情展示监控类型、监控 ID、可用状态、最近采集时间、最近同步尝试时间、最近成功同步时间、陈旧标识及约定核心指标。
- 最后一次成功同步超过 180 秒时显示“数据已陈旧”；从未成功同步时显示 `UNKNOWN`，成功同步后立即清除陈旧标识。
- HertzBeat 停止、超时、部分响应或字段解析失败时，项目、资产、巡检页面仍可用，已有有效数据不被清空，失败原因可在同步运行记录中查看。
- 外部告警恢复不会覆盖联乾侧人工确认、指派和关闭记录；重复拉取保持两类状态各自幂等。
- 会话能力 `canManageIntegrations=false` 时不显示底层组件入口，当前管理员会话该能力为 `true`；访问 HertzBeat 时仍遵循 HertzBeat 自身登录认证。
- 后端测试、前端构建和真实 Docker 端到端验收矩阵全部通过。

## 共享语言与概念边界

- **业务主数据**：项目、环境、服务名称、负责人和连接地址，以联乾数据库为准并向 HertzBeat 推送。
- **运行状态**：监控对象当前可用性，以 HertzBeat 为准；联乾只保存映射、缓存和展示状态。
- **巡检结果**：联乾按计划执行的检查记录，不等同于资产主运行状态。
- **外部告警生命周期**：HertzBeat 返回的 `FIRING` 或 `RESOLVED`，只能由明确外部证据更新。
- **平台处置状态**：联乾侧 `OPEN`、`ACKNOWLEDGED`、`CLOSED` 等人工处理状态；同步任务不得覆盖人工确认、指派或关闭操作。
- **指标**：HertzBeat 采集并返回的时序或最新值；首期由 HertzBeat API 适配器读取。
- **最近采集时间**：HertzBeat 对监控对象最近一次产生采集数据的时间。
- **最近同步尝试时间**：联乾最近一次发起该类外部同步的时间，无论结果成功或失败。
- **最近成功同步时间**：联乾最近一次完整接收并持久化有效数据的时间，是 stale 判定基准。
- **同步运行**：一次手动或定时同步的统一执行记录，包含运行类型、开始/结束时间、状态、处理数量和错误摘要。
- **监控模式**：资产主状态的数据源选择，首期为 `LOCAL` 或 `HERTZBEAT`；只有 `LOCAL` 允许本地巡检写入主状态。
- **映射状态**：HertzBeat 映射生命周期，首期为 `NEVER_SYNCED`、`MANAGED`、`INVALIDATED`、`UNBOUND`，与 `monitorId` 是否为空分开表达。

## 关键决策

- **DEC-1 · 单一日常入口**：联乾是普通用户唯一日常操作入口；HertzBeat 是后台监控引擎。
- **DEC-2 · 状态权威归属**：`monitoringMode=LOCAL` 的资产可由本地巡检更新主状态；`monitoringMode=HERTZBEAT` 的资产无论 `monitorId` 当前是否有效，都由 HertzBeat 路径决定主状态，本地巡检只保留记录。映射失效后保持 `UNKNOWN`，直到重新同步或用户显式切换为 `LOCAL`。
- **DEC-3 · 适配器隔离**：所有 HertzBeat 2.0 API、状态映射、告警映射和指标解析集中在 integration 层，业务层不依赖外部 DTO。
- **DEC-4 · 拉取优先**：首期每 60 秒定时拉取状态和告警，指标按资产详情读取并缓存；接口边界保留后续 Webhook 替换能力。
- **DEC-5 · 失败降级**：外部组件失败不清空最后有效数据，不阻断业务 CRUD；最近成功同步超过 180 秒标记 stale，从未成功则为 `UNKNOWN`。
- **DEC-6 · 明确恢复证据**：告警只能根据 HertzBeat 明确返回的 `resolved` 生命周期数据恢复。查询失败、分页不完整、未知枚举、字段缺失或单项解析失败时只允许新增或更新已成功解析的数据，不允许根据缺席恢复。
- **DEC-7 · 告警双状态**：外部生命周期与平台处置状态分别存储；幂等键为 `source + externalAlertId`，同步只更新外部字段。已恢复告警若 HertzBeat 以同一 externalAlertId 重新触发，则恢复为 `FIRING` 并保留平台处置历史；若返回新 externalAlertId，则创建新告警事件。
- **DEC-8 · 同步单写者**：手动与定时入口调用同一完整同步编排，竞争固定全局租约键 `hertzbeat-observability-sync`；同一时刻只允许一个状态、告警和指标投影运行。运行记录携带版本或开始时间，持久化前拒绝旧运行覆盖较新结果。
- **DEC-9 · 受管标签与删除降级**：`project`、`environment`、`assetId` 由联乾覆盖；资产修改后下次同步覆盖 HertzBeat 手工改动。删除资产时先尝试停用或解绑外部监控；外部清理失败不阻断业务删除，但必须创建可重试的清理任务并在同步运行中记录失败，直到清理成功，避免静默遗留。
- **DEC-10 · 能力位而非完整 RBAC**：本期在会话 DTO 暴露 `canManageIntegrations`，当前单一管理员固定为 `true`，前端据此控制导航；测试使用 `false` 会话 fixture 验证隐藏。不宣称已经提供真实普通账号、HertzBeat 后端代理授权或完整 RBAC。

## 状态与数据时效规则

- `monitoringMode=LOCAL` 且映射状态为 `NEVER_SYNCED` 或 `UNBOUND`：本地巡检可更新资产状态，不显示 HertzBeat stale。
- `monitoringMode=HERTZBEAT` 且映射状态为 `MANAGED`，成功取得状态：按适配器映射为联乾 `UP`、`DOWN` 或 `UNKNOWN`，同时更新最近采集时间和最近成功同步时间并清除 stale。
- `monitoringMode=HERTZBEAT` 且同步失败：保留最后一次 HertzBeat 状态；超过 180 秒标记 stale，不回退为本地巡检状态。
- HertzBeat 返回监控已禁用：资产运行状态显示 `UNKNOWN`，另显示监控已禁用原因。
- HertzBeat 中监控被删除：映射状态改为 `INVALIDATED`，可清除无效 `monitorId`，但保持 `monitoringMode=HERTZBEAT` 和资产状态 `UNKNOWN`；只有重新同步或显式切换 `LOCAL` 才恢复状态写入。
- 资产主动解绑并选择本地监控：映射状态改为 `UNBOUND`、监控模式改为 `LOCAL`，本地巡检从此可更新主状态；资产删除流程按 DEC-9 处理外部清理失败。
- 未知状态枚举、字段缺失或单项解析失败：该资产保留最后有效状态并记录解析错误，不影响同批其他资产。

## 指标契约

- HTTP 监控首期展示可用性、响应时间和 HTTP 状态码；仅在 HertzBeat 2.0 实际响应提供对应字段时展示。
- 端口监控首期展示可用性和连接耗时。
- 内部规范化单位固定为：可用性使用布尔值且无单位，响应时间和连接耗时统一换算为整数毫秒 `ms`，HTTP 状态码使用整数且无单位。适配器负责从 HertzBeat 原始单位转换，无法确认单位的值不入库并记录解析错误。
- 每项指标返回名称、数值、单位、采集时间和最近一小时短时间序列；没有数据时返回明确空状态而不是零值。
- 指标数据超过 180 秒未更新时在视图中标记陈旧；未知指标和单项解析失败不得清空同资产其他有效指标。

## 子项契约

- **ITEM-1 · 外部契约与映射模型**（`cs-feat`）：固定脱敏的 HertzBeat 2.0 状态、告警、已恢复告警和指标响应 fixture；建立内部 DTO、状态映射、`LOCAL/HERTZBEAT` 监控模式、映射生命周期、资产到单一 `monitorId` 映射、受管标签、三类时间字段、stale 和指标单位转换。依赖：无。验收：契约测试覆盖成功、未知字段、未知枚举、字段缺失、未知单位、单项解析失败和外部不可用；失败不得清空最后有效数据。
- **ITEM-2 · 同步运行基础设施**（`cs-feat`）：建立手动/定时共用的完整同步编排、固定全局租约键、运行记录、错误摘要、防旧写和外部清理重试机制；提供 60 秒调度配置。依赖：ITEM-1。验收：手动/定时并发只有一个单写者，任务重启后可再次执行，旧运行不能覆盖新结果，外部清理失败可重试，运行状态可查询。
- **ITEM-3 · 状态回写与权威边界**（`cs-feat`）：实现状态批量拉取和映射，执行状态与数据时效规则，并阻止本地巡检覆盖已同步资产状态。依赖：ITEM-1、ITEM-2。验收：未同步、正常、异常、未知、禁用、外部停机、超时、部分响应、监控删除、解绑、重复同步和重启补偿场景通过。
- **ITEM-4 · 告警闭环**（`cs-feat`）：为 Alert 增加来源、外部告警 ID、外部生命周期、平台处置状态、首次/最后发生和恢复时间；分别查询 HertzBeat 活动与 `resolved` 数据，只根据明确恢复证据更新。依赖：ITEM-1、ITEM-2。验收：`source + externalAlertId` 唯一约束生效；正常、异常、恢复、同 ID 重触发、新 ID 重触发、重复拉取、分页不完整、部分解析失败和跨资产归属场景通过；人工处置字段不被同步覆盖。
- **ITEM-5 · 指标与资产详情**（`cs-feat`）：实现指标适配器、资产监控详情 API 和前端详情视图，展示状态、时效、运行记录摘要、核心指标最新值和最近一小时趋势。依赖：ITEM-1、ITEM-3。验收：HTTP 与端口监控按指标契约展示，单位和时间正确；无指标、陈旧指标、未知指标及部分指标失败均有明确表现。
- **ITEM-6 · 单入口与操作面**（`cs-feat`）：在联乾提供“同步监控数据”入口和最近运行状态；会话 DTO 增加 `canManageIntegrations`，导航按能力位显示，组件访问继续使用 HertzBeat 自身认证。依赖：ITEM-2、ITEM-3、ITEM-4、ITEM-5。验收：手动同步可观察且不绕过互斥；当前管理员会话显示入口，`canManageIntegrations=false` fixture 隐藏入口；组件不可用不阻断核心页面。
- **ITEM-7 · 集成验收与文档**（`cs-review`）：执行真实 Docker 端到端验收矩阵，更新 README 使用说明和架构数据流。依赖：ITEM-1 至 ITEM-6。验收：覆盖正常、异常、明确恢复、重复拉取、HertzBeat 停机、超时、部分响应、字段缺失、重启补偿、监控删除、无指标、手动/定时并发和导航可见性；全部 Epic 验收标准有对应证据。

## 遗留风险

- HertzBeat 2.0 当前发行包 API 仍可能变化，适配器测试必须固定本机实际、脱敏后的响应样例。
- HertzBeat 指标接口的精确路由、字段名和单位需要在 ITEM-1 用本机 2.0 实际响应冻结；若某指标不存在，ITEM-5 按明确空状态处理，不伪造数据。
- 首期拉取告警的及时性受 60 秒同步周期影响；Webhook 作为后续优化。
- `port` 监控只能提供可用性和连接耗时，数据库深度指标需要后续增加安全凭据模型并切换原生数据库监控类型。
- 当前平台只有管理员账号模型；本期只能用会话能力位和 `false` fixture 验证导航分支，真实非管理员账号端到端、多角色权限和 HertzBeat 代理访问控制需要后续独立 Epic。
