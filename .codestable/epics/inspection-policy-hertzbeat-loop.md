# 巡检计划驱动 HertzBeat 监控与告警闭环

## 起点

平台已经能够把服务同步为 HertzBeat Monitor，并持续回写状态、指标和告警；但当前同步入口位于服务管理，Monitor 采集周期固定为 60 秒，巡检计划仍由平台本地调度器执行 TCP 或 HTTP 检查。由此形成两套配置入口和两套执行语义，巡检计划频率不能约束 HertzBeat，用户也无法从计划配置直接得到监控与告警闭环。

## 目标

项目作为被运维系统，服务作为具体监控对象，巡检计划成为 HertzBeat 监控策略的唯一业务配置入口。用户在巡检计划中选择同一项目下的服务，设置统一采集频率、连续失败次数和告警级别；平台保存计划后自动、幂等地向 HertzBeat 同步 Monitor 与告警规则。HertzBeat 按计划频率采集并产生或恢复告警，平台持续回写状态、指标和告警，并提供人工确认和关闭能力。

## 范围

- 扩展项目档案与项目详情，聚合服务状态、巡检计划和告警信息。
- 服务管理只维护监控对象和展示监控结果，不再提供创建或批量同步 HertzBeat Monitor 的入口。
- 一个巡检计划只属于一个项目，包含多个服务，使用一个固定采集频率、一个连续失败次数和一个告警级别。
- 一个服务首期只能属于一个启用中的巡检计划，并继续只对应一个 HertzBeat `monitorId`。
- 保存、修改、启用、停用或删除计划时，写入持久化、版本化的同步任务，再自动同步对应 HertzBeat Monitor 与受管告警规则；计划页同时提供单计划和全部计划的手动补偿同步。
- Monitor 的 `intervals` 来源于巡检计划，不再固定为 60 秒；服务名称、类型、地址和环境仍以平台服务数据为准。
- 平台记录计划级和服务级同步状态、Monitor 与告警规则各自的期望状态和经外部读取验证的实际状态、最近尝试、最近成功、最近一致性校验和失败原因；单个服务失败不回滚同计划其他服务的成功结果。
- HertzBeat 负责周期采集、技术状态、指标、告警触发与恢复；平台负责业务组织、配置同步、结果投影和人工处置。
- 告警中心展示项目、巡检计划、服务、外部生命周期和平台处置状态，并支持确认、备注与关闭。
- 平台定时拉取 HertzBeat 状态、指标和告警的周期独立于 Monitor 采集频率，首期继续使用现有 60 秒同步周期。
- 现有本地检查能力降级为地址测试或未受管服务的临时测试，不再作为启用计划的正式周期执行器，也不得覆盖 HertzBeat 权威状态。
- 迁移现有 Monitor 映射和旧巡检计划；先生成 dry-run 迁移报告，再只认领能由现有外部 ID 唯一证明的 Monitor。无法可靠推断或存在冲突的服务标记为 `MIGRATION_REQUIRED`，保持原执行方式和外部配置，不静默覆盖 HertzBeat 实际配置。

## 非目标

- 不允许同一服务同时属于多个启用中的巡检计划，也不为同一服务创建多个 HertzBeat Monitor。
- 不在平台复制 HertzBeat 完整高级告警规则编辑器、通知渠道和告警模板管理。
- 不实现短信、电话、邮件或企业微信通知渠道管理。
- 不实现数据库 SQL、Redis 命令、日志内容等深度业务检查。
- 不实现自动发现服务、跨多个 HertzBeat 集群或大规模历史指标持久化。
- 不把平台人工处置状态写回为 HertzBeat 的告警恢复状态。
- 不继续把每次 HertzBeat 采样复制为平台巡检执行记录；监控结果以当前状态、指标和状态变化事件表达。
- 不在本 Epic 建设登录日志和业务报错日志。

## 验收标准

- 服务页不再显示单服务或批量“同步监控”操作；未加入计划的服务显示“未配置巡检计划”，并可跳转到计划配置。
- 新增启用计划并选择服务后，平台先保存计划和版本化同步任务，再自动创建或更新 HertzBeat Monitor 与告警规则；外部失败不回滚计划，页面展示失败原因并可手动重试。进程重启后未完成任务能够恢复，旧版本任务不得覆盖新版本配置。
- 计划频率能确定性转换为 HertzBeat `intervals`；例如 1 分钟为 60 秒、5 分钟为 300 秒。修改频率后更新原 Monitor，不创建重复 Monitor。
- 一个服务不能加入两个启用计划；该约束由数据库中的服务级唯一 binding 所有权保证，不只依赖请求前校验。跨项目服务不能加入当前计划；停用计划只有在外部停用成功并进入可接管状态后才释放服务所有权。
- 增加、移除服务以及启用、停用、删除计划时，按操作矩阵更新平台关系、binding、Monitor、告警规则和历史快照；任何外部清理失败都保留可重试载体，不允许先物理删除计划再丢失外部 ID。
- 删除计划使用 `ACTIVE/DISABLED -> DELETING -> DELETED` 逻辑状态；仅当全部受管 Monitor 和告警规则清理成功后进入 `DELETED`。强制结束清理必须是显式人工操作，并保留孤儿资源审计记录。
- 多服务计划同步支持 `NOT_SYNCED`、`SYNCING`、`SYNCED`、`PARTIAL`、`FAILED`；服务级 binding 分别记录 Monitor 与告警规则的期望和实际状态，单个资源失败不影响其他服务同步成功。
- HertzBeat 按计划频率完成采集；对每种受支持服务类型冻结明确的可用性指标、失败条件、无数据和超时语义、恢复条件及 Monitor 重建后的连续计数语义。不具备有效告警契约的服务类型不得启用计划。
- 服务连续失败达到计划阈值后产生 `FIRING` 告警，恢复后返回 `RESOLVED`，平台在既有同步周期内更新且不生成重复告警。
- 告警外部生命周期与平台处置状态分离；`ACKNOWLEDGED` 允许用于持续告警，`CLOSED` 仅允许外部生命周期已为 `RESOLVED`。人工确认或关闭不伪造恢复，同步任务不覆盖人工处置状态。
- HertzBeat 复用同一外部告警 ID 时，只有平台已观察到 `RESOLVED -> FIRING` 状态转换，或外部提供更晚且可证明的新发生标识，才重新打开处置状态并保留上一轮处置历史；轮询重复返回同一个 `FIRING` 必须保持幂等。新外部 ID 创建新告警事件。
- 告警中心支持按项目、计划、服务、级别、外部生命周期、处置状态和时间筛选，并保存处理人、处理时间和备注。
- 项目详情正确展示基本信息、服务状态、巡检计划、活动告警和历史告警聚合。
- HertzBeat 不可用时项目、服务和计划仍可保存与查看，最后有效监控数据不被清空，失败计划可以补偿同步；页面同时展示 `lastCollectedAt`、`lastSyncSucceededAt` 和陈旧状态，旧 `UP` 数据不得被描述为当前正常。
- 旧 Monitor 映射、历史指标和历史告警继续可用；迁移不会重复创建 Monitor 或静默改变无法确认的外部频率。
- 后端自动化测试、前端生产构建和真实 Docker 端到端闭环验证通过。

## 共享语言与概念边界

- **项目**：一个需要被运维的业务系统，是服务、巡检计划和告警的业务归属。
  - 不包括：具体服务器、数据库、Redis、接口等监控对象。
  - 关系 / 不变量：一个巡检计划只属于一个项目，只能选择该项目下的服务。
- **服务**：项目下可被 HertzBeat 监控的具体对象，继续沿用当前 `Asset` 实体和 `/assets` API，不在本 Epic 做破坏性重命名。
  - 不包括：巡检计划、Monitor 或告警规则。
  - 关系 / 不变量：一个服务首期最多对应一个启用计划和一个 HertzBeat Monitor。
- **巡检计划**：平台中的 HertzBeat 监控策略集合，定义一组服务共同使用的采集频率和基础告警策略。
  - 不包括：平台本地调度器产生的一次执行记录。
  - 关系 / 不变量：它是创建、更新、启停 HertzBeat Monitor 与告警规则的唯一业务入口。
- **同步监控配置**：把平台巡检计划和服务资料下发 HertzBeat，创建、更新、启停或清理 Monitor 与告警规则。
  - 不包括：从 HertzBeat 拉取状态和告警，也不等同于刷新页面。
- **同步监控数据**：从 HertzBeat 拉取状态、指标和告警并投影到平台。
  - 不包括：修改 HertzBeat Monitor、频率或告警规则。
- **外部告警生命周期**：HertzBeat 返回的 `FIRING` 或 `RESOLVED`，只由明确外部证据更新。
  - 不包括：平台人工确认或关闭状态。
- **平台处置状态**：平台侧 `OPEN`、`ACKNOWLEDGED`、`CLOSED`，记录运维人员的处理进度。
  - 不包括：服务是否仍然异常。

端到端场景：用户在“订单系统”中维护订单 API 和 Redis，创建“核心服务巡检”计划，选择两个服务、频率 5 分钟、连续失败 2 次、级别 CRITICAL。保存后平台创建或更新两个 Monitor，将 `intervals` 设为 300，并创建对应告警规则。Redis 连续两次采集失败后 HertzBeat 产生 `FIRING` 告警，平台在下一次数据同步后展示该告警；运维人员可以确认告警，但只有 HertzBeat 检测恢复并返回 `RESOLVED` 后，外部生命周期才变为已恢复。

## 关键决策

- **DEC-1 · 巡检计划是唯一配置入口**：服务页移除同步 Monitor 的入口，避免计划频率和 HertzBeat 实际配置出现双写冲突。
- **DEC-2 · HertzBeat 是唯一正式周期执行器**：启用计划不再由平台本地调度器重复执行 TCP 或 HTTP 检查；平台只保留地址测试和补偿工具。
- **DEC-3 · 单服务单启用计划**：首期禁止一个服务同时属于多个启用计划，以匹配一个服务一个 Monitor 和一个采集频率的模型。
- **DEC-4 · 保存与外部同步解耦**：计划先落平台数据库，再执行可重试外部同步；外部失败不回滚业务配置。
- **DEC-5 · 告警由 HertzBeat 产生**：平台不根据服务状态或本地测试结果伪造 HertzBeat 告警，只同步明确的外部告警生命周期。
- **DEC-6 · 双状态告警**：外部生命周期与平台处置状态独立保存，任何一侧同步不得覆盖另一侧状态。
- **DEC-7 · 频率采用固定间隔**：首期仅支持可转换为秒的分钟和小时固定间隔；每日指定时间和任意 Cron 不作为 HertzBeat Monitor 的业务配置。
- **DEC-8 · 版本化持久同步任务**：计划或服务配置每次变化递增期望版本并写入持久化同步任务；同一服务的任务串行执行，执行前后核对当前版本，旧版本任务直接作废，崩溃后的 `SYNCING` 可恢复。
- **DEC-9 · 删除与释放均可补偿**：计划删除采用逻辑状态机，移除服务、停用和删除只有在外部目标状态达成后才释放 binding 所有权；外部失败保留重试数据。
- **DEC-10 · 无监控空窗迁移**：迁移或语义切换只有在 Monitor 与告警规则均同步成功后才停止该服务原有本地周期检查；`MIGRATION_REQUIRED` 服务保持原执行方式。
- **DEC-11 · 重新启用不抢占**：重新启用计划前，必须在一个数据库事务中获取其全部服务的 binding 所有权；任一服务已被其他计划接管，则整项启用请求失败并列出冲突服务，不进入 `PARTIAL`，也不得夺取现有所有权。
- **DEC-12 · 下发成功不等于当前一致**：手动同步和周期 reconciliation 都必须先读取 HertzBeat 外部实际状态，再按最新期望版本修复漂移；页面分别展示“最后下发成功”和“最近验证一致”。

## 配置操作矩阵

| 操作 | 平台计划与关系 | 服务 binding | HertzBeat Monitor | 告警规则 | 历史告警 |
| --- | --- | --- | --- | --- | --- |
| 新增并启用 | 保存计划和服务关系 | 获取唯一所有权，目标 `MANAGED` | 创建或更新并启用 | 创建或更新并启用 | 不变 |
| 修改频率或服务资料 | 保存新期望版本 | 保持所有权 | 按最新版本更新 | 按最新版本校准 | 不变 |
| 增加服务 | 增加关系 | 获取唯一所有权 | 创建或认领唯一 Monitor | 创建或认领受管规则 | 不变 |
| 移除服务 | 关系进入待释放状态 | 外部清理成功后释放 | 停用并删除受管 Monitor | 停用并删除受管规则 | 保留项目、计划、服务快照，可空关联 |
| 停用计划 | 保留计划与关系 | 外部停用成功后标记可接管 | 停用但不删除 | 停用但不删除 | 不变 |
| 重新启用 | 事务内一次性校验并恢复启用目标；任一服务冲突则整体失败 | 只获取未被其他计划占用的全部所有权，绝不抢占 | 启用或重建 | 启用或重建 | 不变 |
| 删除计划 | 状态进入 `DELETING` | 全部清理成功后释放 | 删除；失败则继续重试 | 删除；失败则继续重试 | 永久保留不可变归属快照 |

## 迁移矩阵

| 现状 | 迁移行为 |
| --- | --- |
| 有唯一 Monitor、无旧计划 | dry-run 报告候选；创建默认待确认计划并认领现有外部 ID，不立即改变频率 |
| 有旧计划、无 Monitor | 转换为待同步新计划；在用户确认或迁移批次执行前继续原本地调度 |
| 一个服务命中多个启用旧计划 | 标记 `MIGRATION_REQUIRED`，不创建新 Monitor、不停原调度 |
| Monitor 频率与旧计划冲突 | 标记 `MIGRATION_REQUIRED`，报告双方值，不自动选择权威值 |
| 外部 Monitor 已不存在 | 保留失效映射并标记待修复，确认新计划后重新创建 |
| 多个服务指向同一 Monitor 或重复映射 | 标记 `MIGRATION_REQUIRED`，禁止自动认领和修改外部资源 |

迁移分为 dry-run、确认批次和切换执行权三个阶段。只有 binding 的 Monitor 与告警规则均达到目标 `SYNCED` 后，才停止该服务原有本地周期检查。

## 子项契约

- **ITEM-1 · 数据模型与迁移**（`cs-feat`）：扩展项目档案；为巡检计划增加项目 ID、固定间隔、连续失败次数、告警级别、生命周期和同步聚合字段；建立带数据库唯一所有权的服务 binding、Monitor/规则期望与实际状态、期望版本和持久化同步任务；为告警补充不可变项目/计划/服务快照和人工处置详情；实现 dry-run 迁移报告及分批迁移。依赖：现有监控闭环代码。验收：并发唯一约束、迁移矩阵、逻辑删除、版本作废及历史数据兼容测试通过。
- **ITEM-2 · HertzBeat 配置契约**（`cs-feat`）：冻结本机 HertzBeat 2.0 Monitor 频率、启停和告警规则的真实 API fixture；明确每种受支持服务类型的可用性指标、失败/无数据/超时/恢复和 Monitor 重建语义；冻结可识别同一告警 ID 新 firing 周期的发生时间、恢复时间、事件序列或状态转换字段；扩展客户端读取、创建、更新、停用和删除受管 Monitor 与规则，支持幂等更新和部分失败。依赖：ITEM-1。验收：真实响应契约、频率边界、重复 `FIRING` 幂等、可证明的 `RESOLVED -> FIRING` 重开、未知字段、外部失败、Monitor 或规则被外部删除等测试通过。
- **ITEM-3 · 计划同步编排**（`cs-feat`）：保存后写入版本化持久任务并自动同步；实现单计划和全部计划手动同步，以及周期 reconciliation；每次同步先读取外部实际状态，再按最新期望版本修复被人工修改、停用或删除的资源漂移；同一服务串行处理并拒绝旧版本写回；服务资料和计划配置共同形成 Monitor 期望版本；重新启用必须事务内一次性取得全部服务所有权，任一冲突则整体失败；按配置操作矩阵处理增加/移除服务、频率变化、启停、删除和并发同步；分别记录最后下发成功与最近验证一致时间。依赖：ITEM-1、ITEM-2。验收：全成功、部分成功、漂移修复、重新启用冲突、崩溃恢复、失败重试、防旧写、防重复和外部不可用场景通过。
- **ITEM-4 · 巡检执行语义切换**（`cs-refactor`）：仅在服务 binding 的 Monitor 与告警规则均达到目标 `SYNCED` 后停止该服务原有本地周期检查，把现有检查器收敛为地址测试；`MIGRATION_REQUIRED` 或同步失败服务继续原执行方式；保留历史巡检记录只读兼容，不再让本地结果写入 HertzBeat 受管服务状态。依赖：ITEM-3。验收：切换过程无监控空窗，地址测试不产生正式告警或覆盖权威状态。
